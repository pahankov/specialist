# Online Booking — Система онлайн-записи

Приложение для онлайн-записи клиентов на услуги через веб-интерфейс. Клиент выбирает мастера, услугу и время — мастер управляет записями через админ-панель.

## 🚀 Быстрый старт

### Требования

- **Python** 3.11+
- **Node.js** 20+
- **PostgreSQL** 16 (production, через Docker)

### Запуск

**Быстрый запуск (Windows):**

```
scripts\start.bat              # Backend + Frontend
scripts\run_backend.bat        # Только backend
scripts\run_frontend.bat       # Только frontend
```

**Ручной запуск:**

**Backend:**
```powershell
cd online-booking\backend
$env:PYTHONPATH='.'
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

**Frontend:**
```powershell
cd online-booking\frontend
npm run dev
```

**Docker (production):**
```bash
docker-compose up -d        # Запуск всех сервисов
docker-compose logs -f      # Просмотр логов
docker-compose down         # Остановка
```

### Синхронизация prod → local (только чтение)

Добавленное на сайте (мастера, клиенты, расписание) подтягивается в локальную БД скриптом через admin API — бэкенд менять не нужно:
```powershell
cd online-booking\backend
$env:PROD_EMAIL='admin@example.com'   # PROD_PASSWORD спросит скрыто, в командную строку не пиши
python pull_production.py --dry-run   # только посчитать
python pull_production.py --yes       # залить (сначала спросит, бэкап .db сделает сам)
```
Тянет: страны/города, мастеров (+профили), услуги, рабочие часы, клиентов. Не тянет: записи, пароли (всем ставится dev-пароль из `LOCAL_DEV_PASSWORD`), города пользователей. Обратного направления нет осознанно — прод правится только через сайт/API.

**Автоматически при старте:** `scripts\start.bat` на шаге `[4/8]` подтягивает прод в локальную БД (мастера, клиенты, расписание). Креды берутся из `backend/.env` (`PROD_EMAIL`/`PROD_PASSWORD`, не пушатся); без сети просто предупредит и продолжит с локальной БД. Ничего лишнего запускать не надо.

### Модульная архитектура

Проект использует модульную архитектуру — каждый функциональный блок инкапсулирован в отдельный пакет (`modules/<feature>/`).

**Правила зависимостей:**
```
main.py
  ↓
modules/*
  ↓
services/*, dependencies/*, models/*
  ↓
utils/
```

**Никогда:**
- ❌ `models` не зависит от `modules`
- ❌ `dependencies` не зависит от `modules`
- ❌ `services` не зависит от `modules`

**Преимущества:**
- **Изоляция:** добавление нового модуля не затрагивает другие части кода
- **Масштабируемость:** каждый модуль содержит `router.py` (эндпоинты), `service.py` (бизнес-логика), `dependencies.py` (зависимости)
- **Чистота:** `main.py` — только импорты модулей (7 строк), без бизнес-логики

**Добавление нового модуля:**
```
1. mkdir modules/<feature>/
2. Создать router.py с эндпоинтами
3. Создать __init__.py с экспортом router
4. Добавить одну строку в main.py:
   app.include_router(feature_router, prefix="/api/v1/feature")
```

## 🔐 Разделы интерфейса: /admin и /super

Панель мастера, панель суперадмина и кабинет клиента — **три раздела** одного SPA
на общем шелле `BaseLayout` (сайдбар, гамбургер, хлебные крошки, выход):
свои URL, своё меню, свои guards, свой цвет (мастер — базовый тёмный,
суперадмин — slate, клиент — teal). Общие только UI-компоненты (`PhoneInput`, `CitySelect`, `MasterSelect`, `Modal`) и API-клиент.

| | Мастер (`/admin/*`) | Суперадмин (`/super/*`) | Клиент (`/cabinet`) |
|---|---|---|---|
| Layout | `AdminLayout` — «🍬 Мастерская» | `SuperAdminLayout` — «🛡️ Суперпанель» (тёмная тема) | `ClientLayout` — «💅 Кабинет» (teal) |
| Меню | Дашборд, Мои записи, Мои услуги, Клиенты, Расписание | Дашборд, Доход, Мастера, Все записи, Все клиенты, Расписание, Логи | Мои записи, Записаться |
| Данные | Только свои | Все по системе | Только свои записи |
| Guard | Суперадмина редиректит в `/super/dashboard` | Не-суперадмина редиректит в `/admin/dashboard` | Не-клиента разворачивает по его секции |

Вход — через модалку на главной (`/`), дальше редирект по роли (`getUserRole()` из JWT):
админ → `/super/dashboard`, мастер → `/admin/dashboard`, **клиент → `/cabinet`**.
Префикс текущей секции отдаёт хук `useSectionPrefix()` (`src/utils/section.ts`) — все внутренние ссылки строятся через него, перекрёстных прыжков между разделами нет.

**Суперпользователь** (мастер с `is_admin=true`):
- **Дашборд** — глобальная статистика (все мастера, все записи, все клиенты, общий доход)
- **Доход** — финансовая аналитика, breakdown по мастерам/услугам
- **Мастера** — CRUD, блокировка, bulk-операции, импорт CSV, детальная карточка (статистика, отзывы, аудит, сессии), имперсонация («войти как мастер» → приземление в `/admin`, выход — обратно в `/super/masters`)
- **Все записи / Все клиенты** — пагинация, фильтры, deep-link `?client_id=`
- **Логи** — журнал действий с фильтром по мастеру
- **Экспорт** — CSV с фоновой обработкой (RQ)

**Различие ролей:**
| Функция | Мастер | Суперпользователь | Клиент |
|---------|--------|-------------------|--------|
| Лендинг после входа | `/admin/dashboard` | `/super/dashboard` | `/cabinet` |
| Кабинет | — (своя панель) | — (своя панель) | `/cabinet`: предстоящие + история + отмена своей записи |
| Дашборд | Свои записи, клиенты, услуги | Всё по системе | — |
| Записи | Только свои | Все записи | Только свои (отмена) |
| Услуги | Только свои | — (раздела нет) | — |
| Мастера | — | CRUD + права + блокировка | — (публичный каталог) |
| Доход | — (карточка скрыта) | Полная аналитика | — |

### Сущности

```

  │           ├─ 1:N ──> Service (id, master_id, name, description, duration_minutes, price, is_active, cascade delete)
  │           │           └─ 1:N ──> Appointment
  │           ├─ 1:N ──> Appointment (id, master_id, service_id, client_id, appointment_date, status, notes, cascade delete)
  │           │           └─ N:1 ──> ClientProfile
  │           │           └─ N:1 ──> Service
  │           ├─ 1:N ──> WorkingHour (id, master_id, schedule_date[Date], start_time, end_time)
  │           ├─ 1:N ──> AuditLog (id, master_id, action, entity_type, entity_id, details, ip_address, created_at)
  │           ├─ 1:N ──> BlockedSlot (id, master_id, start_dt, end_dt, reason, created_at)
  │           └─ 1:N ──> RefreshToken (id, user_id, token, expires_at, is_revoked, cascade delete)
  │
  ├─ 1:1 ──> ClientProfile (user_id, no_show_count, preferred_service_ids)
```

### Роли пользователей
- `master` — мастер услуг (может создавать записи, управлять услугами и расписанием)
- `client` — клиент (аутентификация по SMS-коду, без пароля)
- `admin` — суперпользователь (полный доступ ко всей системе)

### Статусы мастеров
- `active` — работает, принимает записи, появляется в публичном каталоге
- `inactive` — не работает (нет активных рабочих дней или сам отключился), не появляется в каталоге
- `suspended` — заблокирован админом (нарушение правил), не может работать

### Статусы записей
- `pending` — ожидает подтверждения
- `confirmed` — подтверждена
- `cancelled` — отменена
- `completed` — завершена

## 🔒 Безопасность

 1. **Пароли:** Bcrypt hashing напрямую (без passlib), валидация: min 8 символов, 1 заглавная, 1 строчная, 1 цифра, 1 спецсимвол (!@#$%^&* и т.д.), 4 уникальных символа
  2. **Аутентификация:** JWT токены (PyJWT, HS256) + refresh token rotation
 3. **SMS OTP:** 6-значный код на телефон (TTL 5 мин), hash-хранение кода, поддержка Twilio/SMS.ru
 4. **Cookies (split-token):** refresh_token — `httponly=True` (7 суток), access_token — `httponly=False`, TTL 30 мин, читается JS для `Authorization: Bearer` (бэк проверяет только header; полный httpOnly — future work)
 5. **Rate limiting:** 60 req/min default, 10 req/min для auth-эндпоинтов
 6. **Валидация:** Pydantic schemas с проверкой типов
 7. **SQL-инъекции:** Защищено SQLAlchemy ORM
 8. **Логирование:** Цветной вывод в консоль (ANSI), SQL-запросы на уровне WARNING, файлы логов с ротацией

## 📚 История версий

### [1.77.0] — 2026-10-18
- **Чекбокс 152-ФЗ закрывает теперь и соцкнопки:** в форме регистрации согласие перенесено наверх и гейтит всё — пока галочка не отмечена, вместо соцсетей показывается подсказка (виджет VK вообще не монтируется, плитки Яндекс/MAX не рендерятся), кнопка «Зарегистрироваться» тоже неактивна. Клик по подсказке только ставит фокус на чекбокс и никогда не отмечает его сам — соц-регистрация без согласия стала невозможна
- **Яндекс и MAX — плитками-иконками под виджетом VK:** полноширинные «Регистрация через Яндекс/MAX» заменены на компактные плитки в ряд. Высота и скругление берутся из общих констант `SOCIAL_BTN_HEIGHT`/`SOCIAL_BTN_RADIUS`, и те же значения уходят в `OAuthListStyles` виджета VK — обе строки выглядят одинаково, хотя VK рисует свои плитки внутри iframe, куда наш CSS не достаёт. У плиток `aria-label`/`title` «Регистрация через …»: на экране чистая иконка, для скринридеров и тестов подпись остаётся
- **Надпись «или войти через VK ID…» менять нельзя:** её рисует сам виджет VK внутри своего iframe, в `OAuthListParams` параметра текста подписи нет (только `container`/`scheme`/`lang`/`styles`) — «зарегистрироваться» вместо «войти» кодом не поставить, пока стоит официальный виджет
- **VK/ОК/Mail — один вход, не три регистрации:** три иконки дают авторизацию своего сервиса, но завершаются через один и тот же бэкенд `/vk/verify` — три двери в один аккаунт системы VK ID
- **Осталось без галочки — вкладка «Войти»:** соцкнопки там доступны без согласия, т.к. рассчитаны на существующий аккаунт; создание нового при первом входе, как и раньше, штампует `consent_*` на сервере. Явное согласие теперь собирается везде, где есть форма регистрации
- **Новые тесты:** 3 кейса в `maxAuth.test.tsx` (соц-блок скрыт до галочки, появляется после неё, подсказка фокусирует чекбокс, но не отмечает его)
- **Цифры тестов:** 578 pytest + 186 vitest

### [1.76.0] — 2026-10-18
- **Соцкнопки в форме регистрации — первым блоком:** в модалку «Регистрация» наверх добавлены виджет VK (OAuthList: VK + Одноклассники + Mail) и кнопки «Регистрация через Яндекс» / «Регистрация через MAX», ниже — разделитель «или заполните форму» и телефон/пароль/чекбокс 152-ФЗ. Соц-регистрация = первый успешный вход у провайдера, согласие штампуется на сервере
- **Данные соцсетей теперь попадают в профиль клиента:** новая колонка `users.avatar_url` (ссылка на CDN VK/Яндекс) + `users.name_source` (откуда имя: `user`/`vk`/`yandex`/`max`), миграция `22a1b2c3d4e7`. В кабинете клиента («Мой профиль») сверху показывается фото из соцсети
- **Умная синхронизация профиля при каждом соц-входе** (`app/services/social_merge.py`, единая для VK/Яндекс/MAX): пустое имя/аватар/email заполняются данными провайдера; имя, **которое человек сам отредактировал** в кабинете или админом (`name_source="user"`), соц-вход не трогает; имя, поставленное соцсетью, при следующем входе обновляется (последний вход главный); email заполняется только в пустое поле и **не перетирает чужой уникальный** адрес; `is_verified` только повышается, никогда не понижается
- **Пометка «имя редактировал человек» в самом узком месте:** `set_full_name`/`set_names` (`app/services/names.py`) ставят `name_source="user"` — так любая человеческая правка имени (кабинет клиента, профиль мастера, админ-CRUD) автоматически защищена от перезаписи соцсетью
- **MAX 503 чинится конфигом сервера** (не кодом): `max_enabled = bool(MAX_BOT_TOKEN)` — добавить `MAX_BOT_TOKEN`/`MAX_BOT_USERNAME`/`MAX_BOT_URL`/`MAX_WEBHOOK_SECRET` в `.env` сервера и перезапустить `beauty-backend`
- **Конфликты данных разобраны и закрыты:** дубли аккаунтов при разных email у VK/Яндекс (привязка только по email), уникальность email/телефона, «скачущее» имя при смене входа, понижение `is_verified`, затирание аватара — все сценарии покрыты «умной» политикой
- **Новые тесты:** 6 кейсов `TestVkProfileSync` (аватар+источник имени при создании, обновление VK-имени/аватара, защита имени человека, монотонность `is_verified`, заполнение email, защита занятого email)
- **Цифры тестов:** 578 pytest + 183 vitest

### [1.75.0] — 2026-10-17
- **Убран переключатель «Войти как Клиент/Мастер»:** вход по умолчанию идёт как клиент — все (включая мастеров) попадают в клиентский кабинет, панель мастера открывается изнутри кабинета. Админы/супер по-прежнему уходят в свою секцию, deep-link (`redirectTo`) сохраняется
- **Согласие 152-ФЗ — только при регистрации:** чекбокс остался единственной точкой явного согласия на форме регистрации (телефон + пароль). Соц-входы (VK/Яндекс/MAX) согласие не спрашивают — первая авторизация через провайдера и есть регистрация, `consent_*` штампуются на сервере неявно; у существующих аккаунтов согласие дозаполняется только если его ещё не было
- **VK-виджет встроен прямо в форму входа:** OAuthList (VK + Одноклассники + Mail) рендерится сразу под разделителем «или» — без отдельного экрана и без галочки. Ошибка конфигурации (503 «не настроен») показывается текстом прямо в виджете, а не тостом при каждом открытии модалки
- **Яндекс и MAX — кнопками с первого экрана:** «Войти через Яндекс» уходит в редирект сразу, «Войти через MAX» открывает флоу получения кода; отдельные экраны-заглушки с согласием удалены
