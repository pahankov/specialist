# MAX: бот, вход и мини-приложение

> Документ описывает текущую интеграцию с мессенджером MAX: чат-бот для входа
> по коду, доставку уведомлений и требования к будущему мини-приложению.
> Реальные токены и секреты здесь не хранятся — только имена переменных
> (`docs/SECRETS.md`).

## 1. Что уже работает

| Возможность | Статус | Код |
|---|---|---|
| Вход/регистрация по коду из диалога бота | ✅ | `app/modules/maxauth/` |
| Привязка MAX-аккаунта к профилю (verified share) | ✅ | `app/modules/maxauth/service.py` |
| Уведомления в MAX (записи, напоминания, сводка мастера) | ✅ | `app/services/notification_dispatch.py` |
| Самовосстановление webhook-подписки | ✅ | `app/services/max_webhook_guard.py` |
| Локальная отладка через long-poll | ✅ | `max_poll.py` |
| Мини-приложение MAX (WebApp SDK + `initData`) | ❌ пока нет | план в §9 |

Публичное имя бота задаётся `MAX_BOT_NAME` (по умолчанию «Электронная запись»).
В API и на сайте бот показывается как `MAX_BOT_USERNAME` / `MAX_BOT_URL`.

## 2. Архитектура

```
Сайт (React)                Backend (FastAPI)                 MAX Bot API
    │                              │                              │
    │ POST /auth/max/start         │                              │
    │ {phone} ────────────────────>│ создаёт OtpCode(channel=max) │
    │<──── deeplink, delivered ────│                              │
    │                              │ push в привязанный диалог ──>│
    │ открывает deeplink           │                              │
    │─────────────────────────────────────────────────────────────>│ bot_started
    │                              │<──── webhook (secret) ───────│
    │                              │<──── request_contact ────────│
    │                              │ HMAC-проверка номера         │
    │                              │<──── send_message(code) ────>│
    │ POST /auth/max/verify        │                              │
    │ {phone, code, consent} ─────>│ проверка хеша OTP            │
    │<──── JWT + cookies ──────────│ создание/вход пользователя   │
```

Код **никогда не возвращается на сайт** в `/max/start`: он существует только
в сообщении бота. На сайте остаётся лишь хеш кода (`OtpCode.code_hash`).

## 3. Пользовательский сценарий

1. Пользователь вводит телефон в модалке входа и нажимает «Получить код в MAX».
2. `POST /api/v1/auth/max/start` создаёт заявку и возвращает:
   - `deeplink` — `https://max.ru/<bot>?start=<otp_id>_<hmac>`;
   - `delivered=true`, если код уже отправлен в ранее привязанный диалог;
   - `expires_in` — TTL кода (по умолчанию 300 секунд).
3. Пользователь открывает бота и нажимает «Поделиться номером».
4. MAX присылает `message_created` с контактом и HMAC-подписью. Бэкенд
   проверяет подпись, сопоставляет номер с заявкой и отправляет код в диалог.
5. Пользователь вводит 6 цифр на сайте → `POST /api/v1/auth/max/verify`.
6. Для нового аккаунта без согласия 152-ФЗ возвращается `challenge` вместо
   сессии; фронт показывает `ConsentScreen` и завершает вход через
   `POST /api/v1/auth/consent/complete`.
7. Для существующего аккаунта сразу выдаются JWT + cookies; роль сохраняется
   (мастер/админ входит в свой раздел, новый пользователь всегда CLIENT).

### Доверие к номеру

- Номер из `request_contact` с корректным `HMAC-SHA256(MAX_BOT_TOKEN, vcf_info)`
  считается подтверждённым платформой: контакт создаётся/обновляется как
  verified, аккаунт привязывается к `users.max_user_id`.
- Текст, набранный в диалоге, и открытие deeplink **не доказывают** владение
  номером: такие события получают только клавиатуру «Поделиться номером»,
  но никогда — код.
- Исключение — push в диалог, уже привязанный к аккаунту ранее проверенным
  контактом.

## 4. Настройка бота (один раз)

1. Создайте бота в кабинете MAX Business / платформы MAX и получите токен.
2. Заполните серверный `online-booking/backend/.env`:

```dotenv
MAX_BOT_TOKEN=<токен бота>
MAX_BOT_USERNAME=<username без @>
MAX_BOT_URL=https://max.ru/<username>      # необязательно, иначе соберётся само
MAX_BOT_NAME=Электронная запись
MAX_WEBHOOK_SECRET=<длинная случайная строка>
MAX_WEBHOOK_URL=https://beauty-specialist.ru/api/max/webhook
# MAX_CA_BUNDLE=/путь/к/russian_trusted_ca.pem   # необязательно
```

3. Перезапустите backend (`sudo systemctl restart beauty-backend`).
4. Подписка на webhook создастся автоматически при старте guard-цикла.
   Ручная проверка/подписка:

```bash
cd online-booking/backend
source venv/bin/activate
python max_webhook.py status
python max_webhook.py subscribe
```

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | да | Токен бота; включает вход через MAX |
| `MAX_BOT_USERNAME` | да | Username для deeplink и кнопки на сайте |
| `MAX_BOT_URL` | нет | Полная ссылка на бота (иначе `https://max.ru/<username>`) |
| `MAX_BOT_NAME` | нет | Подпись кнопки; по умолчанию «Электронная запись» |
| `MAX_WEBHOOK_SECRET` | для webhook | Проверка заголовка `X-Max-Bot-Api-Secret` |
| `MAX_WEBHOOK_URL` | прод | Включает guard самовосстановления подписки |
| `MAX_CA_BUNDLE` | нет | Свой CA-бандл для `platform-api2.max.ru` |

Если `MAX_CA_BUNDLE` пуст, используется `backend/certs/russian_trusted_ca.pem`
(если файл есть), иначе системное хранилище.

## 5. Webhook

- URL: `POST /api/max/webhook` (без `/v1`).
- Секрет: заголовок `X-Max-Bot-Api-Secret`; при несовпадении — `403`.
- Обрабатываемые типы: `message_created`, `bot_started`, `message_callback`.
- MAX ждёт быстрый `2xx`. Ответы в диалог отправляются через `BackgroundTasks`
  после записи в БД; ошибка отправки не превращает доставку в неуспех.
- MAX автоматически отписывает бота, если webhook не отвечал успешно ~8 часов.
  `max_webhook_guard.py` при старте и раз в 10 минут проверяет подписку и
  восстанавливает её. Guard включается только при заданных
  `MAX_WEBHOOK_URL` + `MAX_WEBHOOK_SECRET`.
- Повторная доставка: MAX повторяет update до 10 раз с backoff. Обработчик
  идемпотентен по данным (`OtpCode`, `is_used`), поэтому повторный update не
  создаёт вторую сессию.

### Локальная разработка

Localhost недоступен из интернета, поэтому webhook заменяется long-poll:

```bash
cd online-booking/backend
python max_poll.py
```

Скрипт читает `GET /updates` и пересылает каждый update на
`http://127.0.0.1:8000/api/max/webhook` с тем же секретом. Запускайте backend
и `max_poll.py` в отдельных терминалах.

## 6. API

| Метод | Путь | Тело / ответ |
|---|---|---|
| `POST` | `/api/v1/auth/max/start` | `{phone}` → `{delivered, deeplink, expires_in, bot_username, bot_url, bot_name}`; 10/min |
| `POST` | `/api/v1/auth/max/verify` | `{phone, code, consent}` → JWT/cookies или `{challenge}`; 10/min |
| `POST` | `/api/max/webhook` | update от MAX; секрет в заголовке |

Пример:

```bash
curl -X POST http://localhost:8000/api/v1/auth/max/start \
  -H "Content-Type: application/json" \
  -d '{"phone":"+79991234567"}'
```

Типичные ошибки:

| Код | Причина |
|---|---|
| `400` | неверный код; код выдан для другого номера; номер не подтверждён ботом |
| `410` | код истёк — запросите новый |
| `503` | `MAX_BOT_TOKEN` не задан |
| `403` webhook | несовпадение `MAX_WEBHOOK_SECRET` |

## 7. Уведомления в MAX

- Канал доступен, если у пользователя есть `max_user_id` (то есть он хотя бы
  раз подтвердил номер в боте) и задан `MAX_BOT_TOKEN`.
- Пользователь управляет каналом в «Профиль → Уведомления»:
  `preferred_channel` = `auto` / `max` / `vk` / `email` / `bell`,
  плюс отдельные переключатели `max_enabled`, `reminders_enabled`,
  `master_digest_enabled`.
- `auto` выбирает последний способ входа, затем MAX → VK → email.
- Диспетчер (`notification_dispatch.py`) раз в 15 секунд забирает неотправленные
  уведомления, отправляет их и фиксирует `external_channel` / `external_error`.
- Ссылки в сообщении ведут на `PUBLIC_BASE_URL` и соответствующий раздел
  (`/cabinet`, `/admin`, `/super`).

## 8. Диагностика

| Симптом | Проверка |
|---|---|
| На сайте «Вход через MAX не настроен» | `MAX_BOT_TOKEN` пуст или backend не перезапущен |
| `delivered=false`, код не приходит | Пользователь ещё не привязан: откройте deeplink и поделитесь номером |
| В логах нет `MAX webhook: update_type=...` | Проверьте `python max_webhook.py status` и `MAX_WEBHOOK_URL` |
| Бот перестал получать события | MAX отписал webhook после 8 ч простоя; guard должен восстановить, иначе `subscribe` вручную |
| `401 invalid bot token` | Токен отозван/перевыпущен — обновите `.env` |
| TLS-ошибка к `platform-api2.max.ru` | Укажите `MAX_CA_BUNDLE` или положите `certs/russian_trusted_ca.pem` |

Логи не должны содержать токены и коды. В коде уже маскируются значения
секретов; при диагностике не включайте debug-логи тела webhook в прод.

## 9. Мини-приложение MAX (план)

Сейчас MAX используется только как канал входа и уведомлений: сайт открывается
в обычном браузере. Полноценного мини-приложения (MAX WebApp) в кодовой базе
пока нет. Если оно понадобится, интеграция должна выглядеть так:

1. **Публикация.** В настройках бота указать URL мини-приложения
   (`https://beauty-specialist.ru`) и включить WebApp-режим. MAX открывает
   существующий SPA в своём webview; отдельная сборка не обязательна.
2. **Определение окружения.** Фронт проверяет наличие MAX WebApp SDK и
   получает `initData` (подписанные данные пользователя).
3. **Проверка на сервере.** Новый endpoint (например,
   `POST /api/v1/auth/max/webapp`) принимает `initData`, проверяет
   HMAC-подпись токеном бота и срок жизни, затем находит/создаёт пользователя
   по `max_user_id`. Подпись проверяется только на бэкенде; `initData` нельзя
   считать доверенным на клиенте.
4. **Сессия.** После проверки выдаются те же JWT + cookies, что и в обычном
   входе; фронт переходит в `/cabinet`.
5. **Ограничения webview.** Проверить safe-area, высоту viewport, работу
   `<input type="date">`, загрузку фото и внешних ссылок; для платежей и
   OAuth-редиректов использовать системный браузер.
6. **Безопасность.** Не логировать `initData`; отклонять просроченные данные;
   не принимать `user_id` из query/body без подписи; не отключать проверку
   `state`/PKCE для обычного веб-входа.

До реализации этих пунктов кнопка «Открыть в MAX» должна вести на обычный сайт,
а не выдавать мини-приложение за готовое.
